# 회고

## 무엇을 만들었나

투자일임사 홈페이지에 들어갈 투자 문의 페이지를 작성했다.

일반적인 문의 양식은 "관심 상품", "투자 성향", "희망 수익률" 같은 걸 묻는데, 업계 사람에게는
매일 보는 표현이지만, 금융소비자에게는 다소 생소하거나 벽이 느껴지는 표현일 수 있음.

그래서 어려운 용어로 점철된 질문이 무엇을 묻는지 정확하게 아는 사람만 쓸 수 있는 양식 대신,
질문에 답하는 것만으로 자기에게 필요한 게 무엇인지 알게 되는 화면을 만들었음.

- 실제 사이트: https://project-advisory.vercel.app/inquiry
- 담당자 화면: https://project-advisory.vercel.app/admin/inquiries

---

## 배운 점

### 문서를 먼저 쓰는 게 빠른 길이었음

바로 화면부터 만들고 싶었는데, 먼저 두 가지를 문서로 정했다.

1. **PRD** — 무엇을 만들 것인지, 무엇을 안 만들 것인지
2. **API 명세** — 화면과 서버가 어떻게 대화할지

솔직히 처음엔 "이걸 왜 먼저 쓰지, 시간 아깝다"고 생각했음. 그런데 나중에 저장 방식을
서버 메모리에서 데이터베이스로 통째로 갈았을 때 **화면 코드를 한 줄도 안 고쳤다.**
규격이 그대로였기 때문.

문서를 안 썼으면 백엔드 바꿀 때 화면까지 다 뜯었을 것.

### "내 컴퓨터에서 되니까 됐다"가 아니었음

내 노트북에서 완벽하게 돌아가던 게 인터넷에 올리자마자 깨졌다.

- 문의를 넣었는데 몇 분 뒤 사라짐 → 서버 메모리에만 저장하고 있었고, Vercel은 서버를
  재웠다 깨우면서 메모리를 지움
- 인증번호도 같은 이유로 못 쓰는 구조였음 → 번호를 발급한 서버와 확인하는 서버가 달라질 수 있음

혼자 테스트할 때는 서버가 한 대고 계속 켜져 있으니 이 문제가 아예 안 보였다.
**환경이 달라지면 전제가 무너진다**는 걸 몸으로 배웠음.

### 에러는 한 곳만 보면 안 됨

담당자 화면이 안 열렸을 때 서버 로그를 봤는데 **에러가 하나도 없었다.**
"서버는 정상인데 왜 안 되지?" 하고 한참 헤맸음.

브라우저 콘솔을 보니 400 에러가 있었다. 요청이 **서버에 도착조차 못 한** 것.
서버 로그가 조용한 게 정상이라는 뜻이 아니었음.

### 배포는 "코드를 올리는 것" 이상이었음

Vercel에 GitHub를 연결하기만 하면 끝이라고 생각했다. 실제로는 세 가지가 따로 있었음.

| | 챙겨야 했던 것 |
|---|---|
| 1 | **어느 브랜치**를 올리는지 (기본값이 `main`이라 내 작업 브랜치가 아니었음) |
| 2 | **접속 정보**를 따로 등록 (내 컴퓨터의 `.env.local`은 GitHub에 안 올라감) |
| 3 | 설정을 바꿔도 **다시 배포**해야 반영됨 |

이 중 1번 때문에 "인터넷 사이트에서 넣은 문의가 데이터베이스에 없다"는 문제로 한참 돌았다.

### 나눠두면 나중에 편함

파일을 역할별로 나눠뒀다.

```
src/lib/api/      화면이 서버를 부르는 창구
src/lib/domain/   유형 판정 계산
src/lib/db/       데이터베이스 접근
src/components/   화면 조각
```

그리고 규칙을 하나 세웠음 — **화면 코드는 데이터베이스 파일을 직접 부르지 않는다.**
반드시 `src/lib/api`를 거친다.

이 규칙 하나 때문에 백엔드를 바꿀 때 고칠 곳이 딱 정해졌다. 처음엔 "굳이 이렇게 나눠야 하나"
싶었는데 나중에 값을 했음.

## 잘 됐다고 생각하는 것

**질문을 사람 말로 썼다.** "위험선호도"를 묻지 않고 이렇게 물었음.

> 1년 뒤에 맡긴 돈이 100만 원 중 85만 원으로 줄어 있다면, 어떻게 하시겠어요?

퍼센트(-15%)는 감이 안 오는데 금액은 온다. 이게 이 프로젝트에서 가장 마음에 드는 부분.

**모든 질문에 "잘 모르겠습니다"를 넣었다.** 그리고 그 답이 몇 개인지 담당자 화면에 표시함.
모른다는 답이 많은 사람은 설명이 더 필요한 사람이니, 회피 선택지가 아니라 **정보**로 쓰게 만들었음.

**연습용 데이터를 손으로 안 썼다.** 200줄짜리 SQL을 코드에서 자동 생성하게 했고, 여기에
안전장치를 넣었음. "이 답변 조합은 이 유형이 나와야 한다"고 미리 적어두고, 계산 결과가
다르면 **생성이 아예 실패한다.** 점수 기준을 잘못 고치면 바로 걸림.

**보안을 말로만 확인하지 않았다.** "막아뒀다"고 생각하는 것과 진짜 막혀 있는 건 다르니
직접 공격해 봤음. 열쇠 없이 데이터베이스 열기, 배포된 파일에 열쇠가 섞였는지 검사 등
5가지를 시도했고, 그 과정에서 **실제로 뚫려 있는 구멍 하나를 찾았다.**

## 아쉬운 점

### 보안을 나중으로 미뤘음 — 이게 제일 아쉽다

목업 단계에서 편하게 만들려고 로그인을 우회하는 경로를 남겨뒀다. 내 노트북에서만 돌 때는
아무 문제가 없었음.

그런데 **그 상태로 인터넷에 배포했다.** 결과적으로 주소만 알면 누구나 로그인 없이 문의 목록
전체를 볼 수 있는 상태가 됐음.

지금은 가상 데이터뿐이라 실제 피해는 없다. 하지만 "나중에 막자"고 미뤄둔 걸 잊고 배포 버튼을
눌렀다는 사실 자체가 문제였음. **배포 전에 확인하는 목록을 미리 만들어 뒀어야 했다.**

### 개인정보가 평문으로 저장됨

이름·이메일·전화번호가 데이터베이스에 그대로 들어간다. 암호화를 안 했음.

작업 중에 "해시 처리 됐나?"를 물어봤다가, 이 세 항목은 **해시가 아니라 암호화**를 써야 한다는
걸 알게 됐다. 해시는 되돌릴 수 없어서 비밀번호에 쓰는 것이고, 이메일은 나중에 결과지를
보내야 하니 다시 읽을 수 있어야 함. 개념을 헷갈리고 있었다.

### 테스트를 자동으로 만들지 않았음

매번 브라우저를 열어 클릭하면서 확인했다. 화면이 늘어날수록 확인할 게 늘어나는데,
자동으로 검사하는 코드를 안 만들었음.

특히 유형 판정 계산은 규칙이 복잡해서 자동 테스트가 있었으면 마음이 편했을 것. 연습용 데이터에
넣은 안전장치가 그 역할을 조금 하긴 했지만 그게 전부였다.

### 안 만든 기능이 남아 있음

- 이메일 발송 — 지금은 인증번호를 화면에 띄움
- 결과지 PDF 생성 — 미리보기만 됨
- 법인 고객 흐름 — 만들긴 했는데 끝까지 클릭해 보지 못했음

### 내가 직접 짠 코드가 적음

솔직하게 적자면, 코드 대부분을 AI와 함께 만들었다. 구조와 이유는 설명을 들으며 이해했지만,
**"이걸 나 혼자 처음부터 다시 짤 수 있나?" 하면 아직 아니라고 답해야 함.**

다만 이번에 확실히 얻은 게 있다. 문제가 생겼을 때 어디를 봐야 하는지, 브랜치가 뭔지,
환경 변수가 왜 필요한지, 왜 브라우저가 데이터베이스를 직접 부르면 안 되는지는 이제 설명할 수 있음.
다음엔 더 많은 부분을 직접 판단해 보려고 한다.

## 어려웠던 것

**외부 서비스 화면이 설명과 달랐다.** Supabase의 `API` 메뉴가 `Data API`로 바뀌어 있었고,
Vercel의 `Environment Variables`도 안내받은 위치에 없었음. 화면이 자주 바뀌는 것 같다.
결국 **주소를 직접 입력해서 들어가는 방법**이 제일 확실했다.

**뭐가 어디에 있는지 감이 안 왔다.** "백엔드를 어떻게 봐요?"라고 물어봤을 때, 이미 내가
담당자 화면을 만들어 놨다는 사실을 몰랐음. Supabase 대시보드에서만 볼 수 있는 줄 알았다.
만든 것과 내가 이해한 것 사이에 간격이 있었음.

**호스팅 서비스가 세 개나 필요한 이유.** 처음엔 Supabase 하나로 다 되는 줄 알았다.
가게 자리(Vercel), 창고(Supabase), 우체국(이메일 발송)이 각각 다른 일이라는 걸 이해하는 데
시간이 걸렸음.

## 남은 과제

실제로 고객 문의를 받기 전에 해야 할 것들.

| 순위 | 할 일 | 이유 |
|---|---|---|
| 1 | 담당자 화면 로그인 막기 | 지금 누구나 볼 수 있음 |
| 2 | 담당자 비밀번호를 계정별 해시로 | 공통 비밀번호 하나를 글자 그대로 비교 중 |
| 3 | 개인정보 저장 시 암호화 | 평문 저장 중 |
| 4 | 호출 횟수 제한 | 명세엔 적었는데 구현 안 함 |
| 5 | 이메일 발송 연동 | 국내 메일 도달률 확인 필요 |
| 6 | 확정 안 된 문구 채우기 | 최소 금액, 등급 이름, 법정 고지 문구 |
| 7 | 금융회사 클라우드 이용 절차 확인 | 기술이 아니라 절차 문제 |

7번은 코드로 해결되는 게 아니라는 걸 이번에 알았다. 금융회사가 해외 클라우드에 고객 정보를
두는 데는 따로 밟아야 하는 절차가 있음.

## 느낀 점

**시작할 때 목표는 "내가 웹페이지를 만들 수 있는지 확인해 보는 것"이었다.** 그건 됐음.
화면부터 데이터베이스까지 붙여서 인터넷에 올리고, 실제로 저장되는 것까지 확인했다.

그런데 하다 보니 목표가 바뀌었다. 처음엔 "돌아가게 만드는 것"만 생각했는데, 갈수록
**"돌아가는 것과 쓸 만한 것은 다르다"**는 게 눈에 들어왔음.

메모리에 저장해도 내 노트북에서는 돌아간다. 로그인을 안 막아도 돌아간다. 개인정보를 평문으로
넣어도 돌아간다. 돌아가는 건 시작점이지 도착점이 아니었음.

가장 인상 깊었던 순간은 **보안을 직접 찔러봤을 때**다. 다섯 가지를 시도해서 네 개는 막혀 있고
하나가 뚫려 있었음. 그 하나는 내가 편하려고 만들어 둔 우회 경로였다.
"편의를 위해 남긴 것이 그대로 구멍이 된다"를 눈으로 봤음.

아쉬운 건 아직 내가 코드를 온전히 내 것이라고 말하기 어렵다는 점. 다만 이번엔
**무엇을 물어야 하는지**를 배웠다고 생각한다. "이거 해시 처리 됐어?"라고 물었을 때
"그건 해시가 아니라 암호화를 써야 한다"는 답이 돌아왔는데, 질문이 반쯤 틀렸어도 물어봤기
때문에 개념을 바로잡을 수 있었음.

앞으로 이 프로젝트를 실제 회사 홈페이지로 쓸 생각이다. 그러려면 위에 적은 남은 과제 7개를
하나씩 지워야 함. 특히 1번은 다음에 바로 하려고 한다.
