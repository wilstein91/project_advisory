# 트러블슈팅 기록

만들면서 막혔던 것들과 어떻게 풀었는지 정리했습니다.
같은 문제를 또 만났을 때 처음부터 헤매지 않으려고 남깁니다.

---

## 1. 담당자 화면이 "서버에 연결하지 못했습니다"만 뜬다

**증상**

담당자 문의 목록 화면에 목록이 안 나오고 빨간 안내만 떴습니다.

```
서버에 연결하지 못했습니다. 잠시 후 다시 시도해 주세요.
```

고객 화면(문의 위저드)은 잘 되는데 담당자 화면만 안 됐습니다.

**진단 과정**

서버 로그를 봤는데 **에러가 하나도 없었습니다.** 서버는 요청을 받은 적조차 없다는 뜻이었습니다.
그래서 브라우저 쪽을 봤더니 콘솔에 이게 있었습니다.

```
Failed to load resource: the server responded with a status of 400 (Bad Request)
```

**원인**

담당자를 흉내내려고 요청에 이런 정보를 실어 보냈습니다.

```
x-mock-actor: 김선우
```

HTTP 헤더(요청에 딸려 보내는 짧은 메모 같은 것)에는 **영문·숫자만 담을 수 있습니다.**
한글을 넣으면 브라우저가 요청 자체를 거부합니다. 서버에 도착하지도 못한 겁니다.

**해결**

이름 대신 영문 id를 보내고, 서버가 그 id로 이름을 찾게 바꿨습니다.

```
x-mock-actor: staff_kim     ← 이름이 아니라 id
```

- 고친 곳: [src/lib/api/client.ts](../src/lib/api/client.ts), [src/app/api/v1/[...path]/route.ts](../src/app/api/v1/%5B...path%5D/route.ts)

**배운 것**

에러를 찾을 때 **서버 로그와 브라우저 콘솔을 둘 다 봐야 합니다.**
서버 로그가 조용하면 "서버가 잘 돌고 있다"가 아니라 "요청이 서버까지 못 왔다"일 수도 있습니다.

## 2. 한글 이름이 `?????`로 저장됐다

**증상**

명령줄로 테스트 문의를 넣었더니 담당자 화면에 이름이 이렇게 나왔습니다.

```
INQ-2026-0149   ?????   적극투자형
```

**진단 과정**

처음엔 데이터베이스가 한글을 못 받는 줄 알았습니다. 그런데 미리 넣어둔 연습용 문의
14건(노민석, 윤소미 등)은 한글이 **멀쩡했습니다.**

같은 데이터베이스, 같은 화면인데 어떤 건 깨지고 어떤 건 안 깨진다 → 데이터베이스가 아니라
**넣는 쪽**이 문제라는 뜻이었습니다.

**원인**

Windows에서 `curl` 명령으로 한글이 포함된 데이터를 보낼 때 글자 인코딩이 깨졌습니다.
**앱의 문제가 아니라 테스트 도구의 문제**였습니다.

**해결**

실제 브라우저 화면으로 다시 접수해서 확인했습니다. 정상이었습니다.

```
이름     : 박지우
자유입력 : 한글이 제대로 저장되는지 확인하려고 씁니다.
```

깨진 데이터는 삭제했습니다.

**배운 것**

**테스트 도구가 만든 문제를 앱의 문제로 착각할 수 있습니다.**
"진짜 사용자가 지나는 경로"로 한 번 확인해 봐야 합니다. 여기서는 브라우저였습니다.

## 3. 인터넷 사이트에서 넣은 문의가 데이터베이스에 없다

**증상**

Vercel에 올린 사이트에서 문의를 넣었습니다. 접수번호(`INQ-2026-0148`)까지 정상으로 받았습니다.
그런데 Supabase의 `inquiries` 표를 열어보니 **그 문의가 없었습니다.**

**진단 과정**

처음엔 "Supabase 프로젝트를 두 개 만든 것 아닐까" 의심했습니다. 하지만 아니었습니다.

확실히 가르는 방법을 찾았습니다. 두 버전에 **서로 없는 주소**가 하나씩 있었습니다.

| 주소 | 어느 버전에만 있나 |
|---|---|
| `/api/v1/_health` | Supabase 버전(`practice` 브랜치)에만 |
| `/api/v1/_selfcheck` | 메모리 버전(`main` 브랜치)에만 |

두 개를 실제로 불러봤습니다.

```
/api/v1/_health     → 404  (없는 주소)
/api/v1/_selfcheck  → 200  (있는 주소)
```

**원인**

Vercel은 GitHub를 연결하면 **기본 브랜치(`main`)를 배포**합니다.
Supabase를 붙인 작업은 `practice` 브랜치에 있었고, `main`은 아직 데이터를 서버 메모리에만
저장하는 옛 버전이었습니다.

즉 **인터넷에 올라간 건 Supabase를 모르는 버전**이었습니다.

**해결**

1. Vercel 설정에 Supabase 접속 정보(환경 변수) 2개 등록
2. `practice` 브랜치를 `main`에 합치고 GitHub에 올림
3. Vercel이 자동으로 다시 배포

확인:

```
/api/v1/_health → { "supabase": "connected" }
```

**배운 것**

"코드를 고쳤는데 사이트가 안 바뀐다" 싶으면 **어느 브랜치가 배포됐는지 먼저** 봐야 합니다.
그리고 버전을 구분할 때는 **한쪽에만 있는 주소를 불러보는 방법**이 확실합니다. 추측보다 빠릅니다.

## 4. 넣은 문의가 몇 분 뒤에 사라졌다

**증상**

인터넷 사이트에 문의를 넣고 목록에서 확인했습니다. 15건이었습니다.
몇 분 뒤 다시 보니 **14건으로 돌아가 있었습니다.** 방금 넣은 게 사라졌습니다.

**원인**

그 버전은 문의를 **서버 메모리**에만 저장하고 있었습니다. 메모리는 두 가지 이유로 사라집니다.

1. Vercel은 요청이 없으면 서버를 재웁니다. 다시 깨어날 때 메모리가 초기화됩니다.
2. 접속이 몰리면 서버를 여러 대로 늘립니다. 각 서버는 자기 메모리만 봅니다.
   A 서버에 저장된 게 B 서버에는 없습니다.

내 노트북에서 혼자 테스트할 때는 서버가 한 대고 계속 켜져 있으니 문제가 안 보였습니다.

**해결**

저장 위치를 Supabase(데이터베이스)로 옮겼습니다.

같은 이유로 **이메일 인증번호도 메모리에서 데이터베이스로** 옮겼습니다. 번호를 발급한 서버와
확인하는 서버가 달라지면 "방금 받은 번호가 없는 번호"가 되기 때문입니다.

**배운 것**

목업 단계에서 편하다고 쓴 방식이, 인터넷에 올리는 순간 **쓸 수 없는 방식**이 되기도 합니다.
"내 컴퓨터에서 되니까 됐다"가 아니었습니다.

## 5. 인증번호 요청이 한 번 실패했다가 다음엔 성공했다

**증상**

서버 로그에 이런 게 있었습니다.

```
카탈로그를 불러오지 못했습니다: JWT issued at future
POST /api/v1/email-verifications 500
POST /api/v1/email-verifications 200   ← 바로 다음 시도는 성공
```

**원인**

`JWT issued at future` = "이 열쇠는 미래에 발급된 것이다"라는 뜻입니다.

내 컴퓨터 시계와 Supabase 서버 시계가 몇 초 어긋나 있었습니다. Supabase 입장에서는
아직 오지 않은 시각에 만들어진 열쇠로 보여서 거부한 겁니다.

**해결**

Windows 설정 → 시간 및 언어 → 날짜 및 시간 → **지금 동기화**

**배운 것**

**시계 때문에 나는 오류가 있습니다.** 재현이 안 되고 한 번만 났다 사라지는 오류라면
이런 걸 의심해 볼 만합니다.

## 6. 같은 안내 문구가 두 번 나왔다

**증상**

자산 구성을 고르는 화면에서 같은 문장이 두 번 표시됐습니다.

```
지금 갖고 계신 자산은 대략 어떻게 나뉘어 있나요?

해당되는 것을 모두 골라주세요.
해당되는 것을 모두 골라주세요.   ← 중복
```

**원인**

두 곳에서 같은 문구를 넣고 있었습니다.

1. 문항 데이터에 들어 있는 보조 설명(`help`)
2. 복수 선택 화면이 자동으로 붙이는 안내

**해결**

문항이 이미 보조 설명을 갖고 있으면 화면은 안내를 붙이지 않게 조건을 넣었습니다.

- 고친 곳: [src/components/inquiry/QuestionStep.tsx](../src/components/inquiry/QuestionStep.tsx)

**배운 것**

이건 화면을 실제로 클릭해 보다가 발견했습니다. **직접 써 보지 않으면 안 보이는 문제**가 있습니다.

# 추가로 해 본 것들

문제 해결 말고, 더 잘 만들려고 시도해 본 것들입니다.

## API 명세를 먼저 쓰고 그다음에 화면을 만들었다

화면부터 만들고 싶었는데, 나중에 백엔드를 붙일 걸 알고 있어서 **먼저 규격을 문서로 정했습니다**
([docs/api-spec.md](api-spec.md)).

**효과가 확실했습니다.** 나중에 저장 방식을 메모리에서 Supabase로 통째로 갈았는데,
**화면 코드는 한 줄도 고치지 않았습니다.** 규격이 그대로였기 때문입니다.

## 연습용 데이터를 손으로 안 쓰고 생성기를 만들었다

데이터베이스에 넣을 SQL이 200줄쯤 됐습니다. 손으로 쓰면 오타가 나고, 나중에 점수 기준을
고쳤을 때 데이터와 어긋나는 걸 알아채기 어렵습니다.

그래서 코드에서 읽어 SQL을 만들어 주는 생성기를 만들었습니다
([scripts/generate-seed.ts](../scripts/generate-seed.ts)).

여기에 안전장치를 하나 넣었습니다. 연습용 문의 14건에는 "이 답변 조합은 이 유형이 나와야 한다"는
값을 적어뒀고, **실제 계산 결과가 다르면 생성이 아예 실패**합니다. 점수 기준을 잘못 고치면
바로 걸립니다.

```
seed.sql 생성 완료
  문항 18개 / 선택지 66개
  전략군 5개 / 목업 문의 14건
```

## 질문 문구를 코드가 아니라 데이터베이스에 넣었다

처음에는 질문 문장을 코드 안에 적어뒀습니다. 그런데 이 프로젝트는 아직 확정되지 않은 문구가
많아서(최소 금액, 등급 이름 등) 앞으로 자주 고칠 게 뻔했습니다.

그래서 **문항·선택지·전략군·안내 문구를 전부 데이터베이스 표로 옮겼습니다.**

이제 문구를 고칠 때 코드를 수정하고 다시 배포할 필요가 없습니다. Supabase 화면에서
엑셀처럼 고치면 1분 안에 반영됩니다.

## 보안을 실제로 찔러봤다

"막아뒀다"고 생각하는 것과 진짜 막혀 있는 건 다릅니다. 그래서 직접 공격해 봤습니다.

| 시도한 것 | 결과 |
|---|---|
| 열쇠 없이 데이터베이스 직접 열기 | 401 차단됨 ✅ |
| 틀린 열쇠로 열기 | 401 차단됨 ✅ |
| 배포된 자바스크립트에 열쇠가 섞였는지 검사 | 안 새고 있음 ✅ |
| 인증 없이 담당자 API 부르기 | 401 차단됨 ✅ |
| **우회 헤더로 담당자 API 부르기** | **200 — 18건 전부 조회됨 ⚠** |

마지막 하나가 실제로 뚫려 있었습니다. 목업 단계에서 편하려고 만든 우회 경로가 남아 있어서,
**주소만 알면 로그인 없이 문의 목록 전체를 볼 수 있는 상태**였습니다.

지금은 연습용 가상 데이터뿐이라 실제 피해는 없지만, 진짜 사람의 정보가 들어가기 전에
반드시 막아야 하는 부분으로 기록해 뒀습니다.
