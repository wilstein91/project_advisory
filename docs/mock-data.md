# 투자문의 진단 위저드 — 목업 데이터

PRD의 화면을 실제로 만들면서 붙여 쓸 목업 백엔드입니다. 서버 메모리에만 있어서
개발 서버를 다시 켜면 초기 상태로 돌아갑니다.

## 파일

```
src/lib/mock/
  types.ts      데이터 형태 정의
  catalog.ts    문항 · 전략군 · 유형 이름 · 금액 구간   ← 문구를 고칠 때는 여기만
  scoring.ts    유형 판정 (§7) · 조건부 문항 분기 · 진행률
  fixtures.ts   목업 문의 14건 + 열람 기록
  store.ts      목록 · 조회 · 상태 변경 · 발송 · 이메일 인증
  index.ts      진입점 — 화면에서는 여기서만 가져온다

src/app/api/mock/[...path]/route.ts   목업 API (경로 하나로 전부 처리)
```

## 목업 문의 14건이 덮는 경우

| 항목 | 내용 |
|---|---|
| 유형 5단계 | 안정형 4 · 안정추구형 3 · 위험중립형 2 · 적극투자형 3 · 공격투자형 2 |
| 상태 5단계 | 신규 3 · 검토중 3 · 결과지 발송 2 · 상담 진행 2 · 종료 4 |
| 종료 사유 | 계약 · 금액 미달 · 연락 불가 · 고객 보류 |
| 금액 미달 | `INQ-2026-0131`, `INQ-2026-0146` — 안내 문구 노출 확인용 |
| 모름 응답 많은 건 | `INQ-2026-0141` 윤소미, 4건 |
| 발송 기한 초과 | `INQ-2026-0140`, `INQ-2026-0141`, `INQ-2026-0145` — 목록 맨 위로 올라옴 |
| 조건부 문항 | 채워진 건(`0136`, `0140`, `0144`)과 숨겨진 건 둘 다 |
| 담당자 미배정 | `INQ-2026-0141`과 신규 3건 |
| 자유 입력 빈 건 | `0131`, `0141`, `0143`, `0144`, `0146`, `0147` |

이름·회사명·연락처는 전부 가상이고 이메일은 `example.com`으로 고정했습니다.

## 진단 결과는 저장하지 않습니다

목업 문의에는 답변만 들어 있고, 유형·점수는 `scoring.diagnose()`가 계산합니다.
배점을 고쳤을 때 데이터가 조용히 어긋나는 것을 막기 위해서입니다.

의도한 유형과 실제 계산이 맞는지는 이걸로 확인합니다.

```
GET /api/mock/_selfcheck
```

`mismatches`가 빈 배열이면 정상입니다. 지금 상태에서 14건 전부 일치합니다.

## 엔드포인트

담당자는 `x-mock-actor: 김선우` 헤더로 흉내냅니다(없으면 `운영관리자`).
모든 응답은 화면의 로딩 상태를 만들 수 있게 220ms 늦게 옵니다.

**고객 위저드**

| | |
|---|---|
| `GET /api/mock/questions?segment=individual` | 문항 목록 (분기 규칙 포함) |
| `GET /api/mock/config` | 금액 구간 · 최소 금액 · 상태 이름 |
| `GET /api/mock/strategies` | 전략군 5개 · 유형 이름 · 필수 고지 문장 |
| `POST /api/mock/diagnose` | `{ segment, answers }` → 판정 미리보기 |
| `POST /api/mock/verify/request` | `{ email }` → 인증번호 발송 (목업은 응답에 함께 옴) |
| `POST /api/mock/verify/confirm` | `{ email, code }` |
| `POST /api/mock/inquiries` | 접수. `privacyConsent: true` 없으면 거절 |

**담당자 화면**

| | |
|---|---|
| `GET /api/mock/inquiries` | 목록. `status` `segment` `assignee` `q` `minUnsure` `belowMinimum` 필터 |
| `GET /api/mock/inquiries/{id}` | 상세 + 점수 내역 + 전략군 + 열람 기록 |
| `PATCH /api/mock/inquiries/{id}` | `{ status?, assignee?, closeReason?, closeNote?, memo? }` |
| `POST /api/mock/inquiries/{id}/send-report` | 결과지 발송 |
| `GET /api/mock/audit` | 열람 기록 전체 |

## 화면을 만들 때 주의할 것

**결과를 띄우기 전에 `diagnosis.complete`를 봅니다.** 답변이 덜 찬 상태에서도
판정 함수는 유형을 돌려줍니다(빈 답변이면 `안정형`). 그럴듯해 보이지만 틀린
값이라서, `complete`가 `false`면 결과 화면을 띄우면 안 됩니다.

**다음 문항은 화면에서 정하고, 최종 판정은 서버에서 다시 합니다.**
`questions`가 분기 규칙(`showWhen`)을 그대로 내려주므로 문항을 넘길 때마다
서버에 물어볼 필요가 없습니다. 대신 접수 시점에 서버가 판정을 다시 계산합니다.

**인증번호는 목업에서 `482913` 고정이고 응답에도 들어 있습니다.**
실제 구현에서는 난수로 바꾸고, 응답에 절대 넣지 않습니다.

**미완료 답변을 서버에 보내지 않습니다.** 진행 중인 답은 브라우저에만 두고,
접수 시점에 한 번 보냅니다. 동의 전에 서버에 쌓으면 동의 없는 수집이 됩니다(PRD §11).

## 아직 임시값인 것

`catalog.ts`에 `PLACEHOLDER` 주석이 붙어 있습니다. PRD §15에서 확정되면
그 상수만 고치면 됩니다.

| 값 | PRD | 현재 임시값 |
|---|---|---|
| 최소 가입금액 | §15-1 | 1억 원 |
| 개인 금액 구간 | §15-1 | 3천만 / 1억 / 3억 / 10억 경계 |
| 법인 규모 구간 | §15-1 | 5억 / 20억 / 100억 경계 |
| 전략군 정식 이름 | §15-2 | `원금 지키기 중심` 등 5개 |

전략군 설명 문구에는 숫자가 하나도 들어 있지 않습니다. 예상 수익률·자산 비중·
최대 낙폭은 PRD §3 원칙 3에 따라 넣지 않았고, 문구를 손볼 때도 넣지 않아야 합니다.

## 목업이 아직 흉내내지 않는 것

- 결과지 PDF 실제 생성 — 발송 시각만 기록합니다
- 메일 실제 발송 — 인증번호를 응답으로 돌려주는 것으로 대신합니다
- 담당자 로그인 — 헤더로 대신합니다
- 담당자 알림 메일
